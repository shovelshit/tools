# 猫眼账号维护扫描简化设计

设计修订日期：2026-09-23（北京时间）。范围：仅账号提醒生成、三十天归档、撤销清理的扫描进度与后台维护状态；监控、锁座、通知发送通道和业务时间窗口不变。

状态：已由用户人工复核并批准实施，本地实现与测试已完成；生产 D1 索引迁移和 Worker 发布尚未执行。此修订替代此前设计中“跨日分页游标决定下一次扫描起点”的部分。

## 选择与取舍

保留 `maoyan_maintenance_runs` 作为每个 `(job_id, local_date)` 的执行结果记录，不再依赖持久化 `cursor` 续跑。保留 `lease_until` 的短租约及条件更新，仅用来避免同一任务的并发 cron 相互覆盖结果；`completed_at` 表示最近一次完整扫描成功，不能阻止同一天后续 cron 再检查。这样继续兼容已提交的 D1 加法迁移，不删除现有列或生产数据。代价是表仍有一个并发字段；完全去掉租约虽然更简短，但同一任务重叠运行时需要额外处理较旧运行覆盖较新结果。

每次维护窗口内的 cron 按北京时间当天重新查候选，而不是从昨日账号 ID 接续。提醒只选当日有效的 `one-day`、`three-day` 和已到期阶段，并用出箱唯一 `event_key` 排除已入队记录；事件键仍由账号、到期时刻和阶段组成。归档只选当前满足三十天条件且 `archived_at IS NULL` 的账号；撤销只选 `revocation_cleanup` 尚有标记的账号。归档和撤销完成后，候选会从查询结果中消失，次日自然处理剩余记录。提醒错过对应自然日后不补发旧阶段，发送前仍重验账号当前有效期与日期。

每次 cron 对每个任务最多处理一页 50 条，避免维护工作占用监控批次。查询必须排除已成功处理的候选，不能重复取同一页使后续账号得不到机会。处理失败时保留未完成状态和原业务标记，下个维护 tick 再试；持续失败的候选占满一页时记录积压告警，不将当天误记为完成。账号或期限在窗口内变化后，下个 tick 继续扫描，即使此前已经有 `completed_at`。

## 每日状态

维护窗口结束后的第一次 cron 仅核验当日结果，不在窗口外生成或发送到期提醒。对 `reminder`、`archive`、`revocation` 分别显示：无当日执行记录为“未执行”；有记录但本日最后一次扫描失败、达到一页上限后仍有候选或关窗核验仍有候选为“未完成”；至少一次完整扫描成功且关窗核验无候选为“已完成”，包括没有符合条件账号的日期。这个状态只描述扫描和出箱入队，不代表推送渠道已送达。推送成功/失败继续由通知出箱单独展示。

管理员在当日修改维护窗口时按新策略决定下一次准入；若窗口重新开放，同日扫描和记录可以更新，直到北京时间日期结束才定稿，历史日期不按此后的新策略重判。已经接纳的任务可以完成本页，但关窗后不启动新的维护扫描。首次运行时用一条审计事件记录观测起点；首次观测晚于当天窗口结束及更早的日期显示“未开始观测”，不能误报为未执行。已有的最近维护日期看板扩展为三类任务的状态和最后完成时刻。
