## 二、缺陷详情

### BUG-1 [高] 未开启监控的配置会被 cron 写入「监控已到期」

**位置**：`worker/src/maoyan/ddl.js`（`isExpired`） → `worker/src/maoyan/check.js:22-37` → `worker/src/maoyan/tokens.js`（`runScheduledChecks`）

**复现步骤**：某令牌已保存影院（config 里有 `cinemaId`，但从未点过「开始监控」，因此没有 `enabled` 字段）→ 等一次 cron 批次（或本地触发 `__scheduled`）。

**实测证据**：本地隔离实例中，触发 cron 前 `changes: []`；触发后变为：

```json
[{"time":"2026-09-12T03:16:56.463Z","type":"warn",
  "text":"监控已到期（截止 未设置），已自动停止；在监控页点「开始监控」可再续 30 天"}]
```

**根因**：
- `isExpired(cfg)`：`enabled !== false` 且 `!cfg.monitorDdl` → 判定为"已过期"。
- 前端加载影院时会自动保存 `{cinemaId, selectedMovieIds, notifyChannel}`，**不写 `enabled`**，所以 `enabled` 为 `undefined`，被误判成"到期"。
- `runScheduledChecks` 会遍历**所有**令牌，因此每个"只选好影院还没开始监控"的用户都会中招。

**影响**：变化记录出现误导性告警并顺带把 `enabled` 落成 `false`；用户会以为功能坏了。

**修复建议（任选）**：
1. `isExpired` 起始加 `if (cfg.enabled !== true) return false;`
2. 或 `runCheck` 中仅在 `cfg.enabled === true` 时才走到期逻辑。

### BUG-2 [中] 「立即检查」在未监控/未配置影院时仍报“检查完成”

**位置**：`worker/src/index.js:111-113`（`json(await runCheck(env, true, token))` 固定 200） + `pages/maoyan/app.js:787-798`

**实测证据**（停止监控状态下 POST `/api/check`）：

```http
HTTP/1.1 200 OK
{"ok":false,"error":"监控已停止，请先在界面恢复监控"}
```

前端 `api()` 只依据 HTTP 状态判定成败，因此走成功分支，记录日志
`检查完成: ，新增 0 场`（影院名为空、数量为 0），实际什么都没检查。

**影响**：用户看到"假成功"，无法区分"检查了但无新增"与"根本没检查"。

**修复建议**：`runCheck` 业务失败时返回 4xx（与 `/api/cinemas`、`/api/lock/*` 的 400 风格一致），或前端额外判断 `res.ok`。

---

### BUG-3 [中] 手动停止监控后状态栏会变成「已到期」

**位置**：`pages/maoyan/app.js:833-843`

**实测证据**（服务端在手动停止后仍保留未来的 `monitorDdl`）：

```json
GET /api/status → {"status":{"enabled":false,"monitorDdl":"2026-10-12T02:53:13.900Z"}}
```

前端计算：

```js
const stopped = status.enabled === false;
const expired = stopped && monitorDdl && Date.now() > Date.parse(monitorDdl); // 计算后被丢弃（死代码）
const main = stopped ? (monitorDdl ? "已到期" : "已停止") : ...;              // 只看 monitorDdl 有没有值
```

**复现步骤**：开始监控 → 点「停止监控」（此时显示"已停止"）→ 等 60 秒自动刷新（`setInterval(refreshChanges, 60000)`）→ 状态栏变成「已到期 · 截止 2026-10-12 · 上次检查 …」。

**影响**：停止监控后文案与事实矛盾，且一分钟内自动翻转，用户会困惑（"我没到期怎么就到期了"）。

**修复建议**：`const main = stopped ? (expired ? "已到期" : "已停止") : ...`，即改用已有的 `expired`。

### BUG-4 [中] 运行中可切到未配置的推送渠道，推送静默失效

**位置**：`worker/src/index.js:92-107`

**实测证据**（令牌为"运行中 + Bark 已验证"，切到 Server酱 且未填 SendKey）：

```json
POST /api/config {"notifyChannel":"serverchan"}
→ {"ok":true,"config":{"notifyChannel":"serverchan","enabled":true,
   "hasBark":true,"hasServerChan":false,"notifyVerified":false}}
```

`enabled` 仍为 `true`。因为"凭据校验"和"测试推送校验"只在请求体带 `enabled` 字段时才执行，而前端切换渠道只提交 `notifyChannel`。

**影响**：监控继续运行，但之后每次新增场次的推送都会失败（`Server酱 未配置`），手机端收不到通知；只有变化记录里一条 error，管理页仍显示"监控中"——**静默失效**，用户很可能长期不知道漏了通知。

**修复建议**：当 `cfg.enabled === true` 且请求要切换渠道时，校验新渠道凭据 + 是否已验证；不满足则拒绝（或先自动停止监控并提示）。

### BUG-5 [低] cinemaId 未做格式校验

**位置**：`worker/src/index.js:84-87`（仅 `String().trim()`）

**实测证据**：`POST /api/config {"cinemaId":"abc"}` → `200 {"ok":true,...,"cinemaId":"abc"}`；随后
`GET /api/shows?cinemaId=abc` → `500 {"ok":false,"error":"接口数据异常(缺少 showData.movies)"}`。

**影响**：非法值被持久化，之后每次加载影院都失败，用户需手动改回；同时把上游异常暴露成 500。

**修复建议**：`cinemaId` 校验 `/^\d+$/`，不合规直接 400。

---

### BUG-6 [低] 前端单测在 Windows(CRLF) 环境必然失败

**位置**：`pages/maoyan/app.test.cjs:16`

```js
assert.match(source, /await buttonLoading\(els\.submit,[\s\S]*?\n\s*renderSelection\(\);\n\s*}/);
```

该正则要求 `;` 后紧跟 `\n`，但 `pages/maoyan/lock.js` 在工作区是 CRLF（`;` 后是 `\r\n`）。

**实测证据**：

```
# tests 13  # pass 12  # fail 1
not ok 2 - lock submission restores disabled state after the loading button resets
```

行尾核查：仓库 index 为 LF，但仓库**没有 `.gitattributes`**，本机 `core.autocrlf=true` → 检出即 CRLF；`lock.js` 实测 648/648 行全为 CRLF。

**影响**：任何 Windows 检出（默认配置）都跑不绿这套测试，真实回归会被这条常驻红掩盖。

**修复建议**：加 `.gitattributes`（如 `* text=auto eol=lf`），或测试里先 `const source = raw.replace(/\r\n/g, "\n")`。

## 三、次要问题 / 观察项

1. **HTTP 语义不统一**：`/api/shows`、`/api/check`、`/api/config` 的业务失败普遍返回 `200 + ok:false`，而 `/api/cinemas`、`/api/lock/*` 用 400/404/409。前端 `api()` 只看 HTTP 状态，容易误判（BUG-2 即此）。
2. **初始文案与实际不符**：`pages/maoyan/index.html:105` 的 `batch-tip` 硬编码"每 10 分钟一批"，实际 cron 为 30 分钟；`app.js` 初始化会覆盖，但会一闪。
3. **遗留接口**：`/api/test-bark` 仍存在（前端已改用 `/api/test-push`）；当当前渠道是 Server酱 时会 500。
4. **令牌比较**：`tokens.js: checkAuthFull` 用 `===` 比对（非恒定时间）；实际风险低，可在加固时一并处理。
5. **硬编码**：`cron.js` 的 `SCRIPT_NAME = "tools-api"`；`minBatchMinutes` 兜底值 10 与 `CRON_EXPRESSION` 的 30 不一致。

## 五、文档/流程偏差（DOC-1，待决策）

`~/.workbuddy/skills/tools-site-deploy/SKILL.md` 的描述与当前实际已明显脱节：

| skill 描述 | 实际情况 |
| --- | --- |
| 本地工作区 `tools/`（含 `maoyan/`、`store/`） | 实际为 `pages/`（`pages/maoyan/`、`pages/store/`） |
| API Worker 在 `maoyan-cloud/`，配置 `wrangler.api.toml` | 实际为 `worker/`，配置 `worker/wrangler.toml` |
| 双 Worker：`tools-api` + `tools-cron`（KV `meta:cron_tokens` 同步） | 已合并为**单 Worker `tools-api`**（同时含 fetch 与 scheduled）；`tools-cron` 已不存在；KV 中也没有 `meta:cron_tokens` |
| 部署必须 `--branch=main`（production_branch=main） | Pages 项目生产分支现为 **`master`**，且已接 Git 集成（push 自动生产部署） |

**风险**：照 skill 执行 `wrangler pages deploy . --branch=main` 会落到 **Preview** 环境，自定义域不会更新——正是 skill 自己警告过的"自定义域行为与最新部署不一致"症状。

**建议**：更新 skill（目录、单 Worker 架构、生产分支 `master`、Git 集成自动部署）。
